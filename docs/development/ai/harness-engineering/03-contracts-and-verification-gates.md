## AI 작업을 신뢰할 수 있게 만드는 계약과 검증 게이트

2편에서는 Agent, Skill, Tool, Orchestrator가 서로 다른 책임을 맡는다는 점을 살펴봤습니다. 하지만 역할을 나누는 것만으로는 충분하지 않습니다. 각 단계가 어떤 입력을 받고, 어떤 결과를 내며, 무엇을 실패로 처리해야 하는지 합의하지 않으면 작업은 다시 자연어 해석에 의존하게 됩니다.

이 글에서는 AI가 수행한 작업을 신뢰할 수 있도록 입력·산출물·부작용을 계약으로 표현하고, 계약을 통과한 결과만 다음 단계로 넘기는 검증 게이트를 살펴봅니다.

## 검증은 왜 필요한가

AI가 “대상자 목록을 만들었습니다”라고 보고하는 것은 작업 결과에 대한 주장입니다. 이 말만으로는 목록이 실제로 존재하는지, 발급 조건을 모두 적용했는지, 원본 수강 기록을 훼손하지 않았는지 알 수 없습니다.

검증은 AI의 답변을 믿지 못해서만 필요한 것이 아닙니다. 사람이 작성한 코드나 사람이 만든 파일도 같은 기준으로 확인해야 합니다. 중요한 것은 누가 결과를 만들었는가가 아니라, **업무 규칙에 따라 결과와 부작용을 다시 확인할 수 있는가**입니다.

수료증 발급의 경우 다음 두 문장은 서로 다릅니다.

```text
"민지와 도윤을 발급 대상으로 만들었습니다."

"목록 파일에 민지와 도윤만 있고, 두 사람의 조건이 맞으며,
원본 수강 기록도 변경되지 않았음을 확인했습니다."
```

첫 번째는 완료 보고이고, 두 번째는 검증 근거가 있는 완료 판정입니다. 하네스에서는 두 번째 상태에 도달해야 실제 발급 같은 후속 작업을 진행합니다.

## 입력 계약: 어떤 요청만 받을 것인가

### 발급 조건의 형식과 범위

입력 계약은 시스템이 어떤 요청을 받아들일지 정하는 약속입니다. 수료증 발급 요청에는 단순히 “대상자를 뽑아 주세요”라는 문장만 있는 것이 아니라, 적용할 기준과 그 기준의 의미가 포함되어야 합니다.

예를 들어 다음과 같은 정보가 계약에 들어갈 수 있습니다.

| 항목        | 예시                                | 필요한 이유                                     |
| ----------- | ----------------------------------- | ----------------------------------------------- |
| 과정 식별자 | `backend-basic-2026-10`             | 어느 과정의 기록인지 구분합니다.                |
| 출석 기준   | `80`                                | 경계값을 일관되게 적용합니다.                   |
| 과제 조건   | `모두 제출`                         | 미제출자의 처리 기준을 고정합니다.              |
| 미납자 처리 | `제외`                              | 수료 조건과 운영 정책을 분리해 명시합니다.      |
| 결과 경로   | `output/certificate-candidates.csv` | 허용되지 않은 위치에 파일을 만들지 않게 합니다. |

입력 계약이 없으면 “이번 달”, “출석률이 높은 사람”, “과제를 거의 다 낸 사람”처럼 해석이 갈릴 수 있는 표현이 작업마다 다르게 처리될 수 있습니다. 계약은 모델의 추론을 대신하는 것이 아니라, 업무에서 이미 정해야 하는 기준을 명확한 데이터로 옮기는 일입니다.

### 잘못된 기준값은 왜 자동 보정하지 않는가

출석 기준이 `"80%"`처럼 문자열로 들어오거나, `-10` 또는 `180`처럼 범위를 벗어난 값이 들어오면 어떻게 해야 할까요? 시스템이 편의상 값을 추측해 고치면 요청자의 의도와 다른 결과를 만들 수 있습니다.

예를 들어 출석 기준 `80`을 `8`로 잘못 입력했을 때, 시스템이 이를 자동 보정하지 못하면 과도하게 많은 수강생이 발급 대상에 들어갈 수 있습니다. 이런 경우에는 잘못된 요청이라는 사실을 명확히 반환하고, 기준을 확인한 뒤 다시 요청하게 하는 편이 안전합니다.

입력 오류를 조기에 막으면, 잘못된 기준으로 생성된 결과를 나중에 되돌리는 비용도 줄일 수 있습니다.

## 산출물 계약: 무엇을 검사할 것인가

| 검사 항목 | 수료증 발급 예시                        |
| --------- | --------------------------------------- |
| 형식      | 대상자 목록에 필요한 식별 정보가 있는가 |
| 대상자    | 민지·도윤만 포함되는가                  |
| 조건 근거 | 출석률과 과제 제출 상태가 일치하는가    |
| 부작용    | 원본 수강 기록이 바뀌지 않았는가        |

산출물 계약은 “어떤 결과를 성공으로 인정할 것인가”를 정합니다. 발급 대상 목록이 CSV, 데이터베이스 레코드, API 응답 중 어떤 형식이든 다음 네 층을 나누어 살펴보는 것이 좋습니다.

1. **형식**: 파일이나 응답이 존재하고, 필요한 식별 정보와 열을 갖추었는지 확인합니다.
2. **대상자**: 기대한 사람만 포함되고, 중복이나 누락이 없는지 확인합니다.
3. **조건 근거**: 각 대상자가 출석·과제·미납 조건을 실제로 충족하는지 확인합니다.
4. **부작용**: 원본 기록, 이전 발급 목록, 허용되지 않은 경로가 바뀌지 않았는지 확인합니다.

AI가 `ok: true`와 같은 성공 표시를 남겨도 이를 검증 결과로 받아들이면 안 됩니다. 성공 표시는 생성 주체의 자기 보고일 뿐이며, 검증기는 실제 산출물과 독립 기준을 대조해야 합니다.

## 합계만 맞아도 틀릴 수 있다

결과를 검증할 때 집계값만 비교하면 중요한 오류를 놓칠 수 있습니다. 수료증 발급 대상이 두 명이어야 한다는 조건만 검사하면, 아래 두 결과가 모두 통과합니다.

| 후보 목록  | 대상자 수 | 실제 판정 |
| ---------- | --------: | --------- |
| 민지, 도윤 |       2명 | 정상      |
| 민지, 준호 |       2명 | 오류      |

두 번째 목록은 대상자 수가 같지만, 과제를 제출하지 않은 준호가 포함되어 있고 도윤이 빠져 있습니다. 이 오류는 대상자별 조건을 확인하지 않으면 발견할 수 없습니다.

실무에서는 금액 합계, 주문 건수, 사용자 수처럼 요약 수치가 맞더라도 개별 레코드가 틀린 경우가 자주 발생합니다. 따라서 검증은 “총 몇 건인가”에서 끝나지 않고, “어떤 항목이 어떤 근거로 포함됐는가”까지 내려가야 합니다.

## 실패는 이유를 가진 데이터여야 한다

### 잘못된 요청

과정 식별자가 없거나, 출석 기준이 범위를 벗어나거나, 허용하지 않은 조건 필드가 들어온 경우입니다. 이 문제는 산출물을 만들기 전에 막아야 합니다.

예를 들어 `ATTENDANCE_THRESHOLD_INVALID`처럼 원인을 나타내는 코드와 함께 반환하면, 요청을 수정해야 하는 사람과 구현을 수정해야 하는 사람이 서로 다른 문제임을 구분할 수 있습니다.

### 산출물 없음

AI가 생성했다고 보고했지만 결과 파일이 없거나, 결과 경로가 허용된 출력 폴더 밖을 가리키는 경우입니다. 이는 단순히 다시 시도할 문제가 아니라 파일 생성 과정과 경로 정책을 확인해야 하는 실패입니다.

이 경우에는 `ARTIFACT_MISSING` 또는 `ARTIFACT_PATH_INVALID`처럼 결과물 자체에 문제가 있음을 나타낼 수 있습니다.

### 조건 불일치

대상자 목록에 미제출자나 미납자가 포함되거나, 조건을 충족한 수강생이 누락된 경우입니다. 대상자 수가 맞더라도 사람별 조건이 다르면 실패입니다.

예를 들어 `CANDIDATES_MISMATCH`와 `ELIGIBILITY_RULE_VIOLATION`을 구분하면, 목록 자체가 기대값과 다른 문제와 어떤 조건이 위반됐는지를 각각 추적할 수 있습니다.

### 원본 변경

발급 대상 목록을 생성하는 중 수강 기록이 변경됐다면 결과가 맞아도 승인하면 안 됩니다. 원본 변경은 잘못된 계산과는 성격이 다른 문제이므로 별도 실패로 남겨야 합니다.

원본의 해시나 버전을 비교해 `SOURCE_CHANGED`를 기록하면, 나중에 왜 발급이 중단됐는지 추적할 수 있습니다. 다만 해시는 변경을 발견하는 도구일 뿐, 실제 쓰기를 막는 권한 제어를 대신하지는 않습니다.

## 검증 게이트와 완료 판정

검증 게이트는 계약 검사 결과를 다음 단계의 조건으로 연결합니다. 발급 대상 목록을 만들었다고 해서 바로 수료증을 발급하는 것이 아니라, 필요한 검증이 모두 통과했을 때만 다음 단계로 진행합니다.

```text
요청 계약 검사
→ 대상자 목록 생성
→ 산출물 계약 검사
→ 원본 무결성 검사
→ 모든 검사 통과 시 발급 승인
```

여기서 어느 단계라도 실패했다면 후속 단계는 실행하지 않거나, 실행하지 않았다는 사실을 명확히 남겨야 합니다. 예를 들어 산출물 계약에서 대상자 오류가 발견됐다면 실제 발급은 `BLOCK`이고, 발급 단계는 `SKIP`입니다.

`BLOCK`과 `SKIP`을 구분하면 문제 분석이 쉬워집니다. `BLOCK`은 실행했지만 기준을 통과하지 못했다는 뜻이고, `SKIP`은 선행 조건이 충족되지 않아 아예 실행하지 않았다는 뜻입니다. 둘을 모두 실패로 뭉뚱그리면 어디서 문제가 시작됐는지 알기 어렵습니다.

검증 게이트의 목적은 AI의 결과를 불필요하게 늦추는 것이 아닙니다. 잘못된 결과가 발급, 배포, 고객 알림처럼 되돌리기 어려운 단계로 넘어가기 전에 멈추게 하는 것입니다.

## 정리

- 입력 계약은 어떤 요청을 받아들일지 정해, 잘못된 기준으로 작업이 시작되는 일을 막습니다.
- 산출물 계약은 형식, 대상자, 조건 근거, 부작용을 나누어 실제 결과를 검증합니다.
- 대상자 수나 합계 같은 요약값이 맞아도 개별 항목이 틀릴 수 있으므로, 레코드 단위 검증이 필요합니다.
- 실패 코드는 원인을 설명하는 데이터이므로 재시도, 수정, 중단 같은 다음 행동을 구분하게 해 줍니다.
- 검증 게이트는 모든 기준을 통과한 결과만 되돌리기 어려운 다음 단계로 전달합니다.
