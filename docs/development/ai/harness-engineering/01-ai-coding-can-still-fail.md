## AI의 정답과 업무 성공 사이, 하네스 엔지니어링

AI에게 기능 하나를 구현해 달라고 요청했을 때, 우리는 흔히 결과가 맞으면 작업도 성공했다고 생각합니다. 예를 들어 “수료증 발급 대상자 목록을 만들어 달라”는 요청에 AI가 정확한 명단을 만들었다면, 겉으로는 문제가 없어 보입니다.

하지만 실제 업무에서는 결과 파일 하나만 맞는다고 성공이 되지는 않습니다. 원본 데이터가 훼손되지 않았는지, 정해진 조건을 빠뜨리지 않았는지, 허용되지 않은 파일까지 수정하지 않았는지, 그리고 누군가가 나중에 그 결과를 다시 확인할 수 있는지가 함께 중요합니다.

이 글에서는 AI가 만든 기능이 맞는데도 업무가 실패할 수 있는 이유를 살펴봅니다. 이어서 이런 실패를 줄이기 위해 AI 주변의 실행 조건과 검증 흐름을 설계하는 하네스 엔지니어링을 정리합니다.

## 한 줄 요약

**기능의 정답은 업무 성공의 한 조건일 뿐입니다.** 업무가 성공하려면 결과의 정확성뿐 아니라 데이터 보존, 변경 범위, 검증 근거까지 확인해야 합니다.

## 예시: 수료증 발급 대상 목록

온라인 교육 플랫폼을 운영한다고 가정해 보겠습니다. 운영 담당자는 다음과 같이 요청합니다.

> 이번 달 과정에서 출석률이 80% 이상이고 과제를 모두 제출한 수강생에게만 수료증을 발급해 주세요. 기존 수강 기록은 수정하면 안 됩니다.

수강 기록은 다음과 같습니다.

| 수강생 | 출석률 | 과제 제출 | 기대 결과 |
| ------ | -----: | --------- | --------- |
| 민지   |    92% | 완료      | 발급 대상 |
| 준호   |    85% | 미제출    | 제외      |
| 서연   |    78% | 완료      | 제외      |
| 도윤   |    80% | 완료      | 발급 대상 |

이 요청의 기대 결과는 민지와 도윤, 두 명으로 이루어진 발급 대상 목록입니다. 출석률 80%는 포함 조건이므로 도윤은 대상에 포함되어야 하고, 출석률이 충분한 준호도 과제를 제출하지 않았으므로 제외되어야 합니다.

AI가 아래와 같은 목록을 만들었다면 기능 관점에서는 정답입니다.

```text
2026년 10월 수료증 발급 대상
- 민지
- 도윤
```

그런데 이 결과만 보고 작업을 완료 처리해도 될까요?

## 기능이 맞아도 실패하는 경우

### 대상자 목록은 맞지만 원본 수강 기록을 수정한 경우

AI가 대상자 목록을 만들기 쉽도록 원본 수강 기록에 `발급 여부` 열을 추가하거나, 준호의 과제 상태를 임의로 `완료`로 바꿨다고 해 보겠습니다. 최종 목록이 민지와 도윤으로 맞더라도, 원본 기록은 더 이상 원래의 업무 데이터가 아닙니다.

원본 데이터는 이후 출석 분석, 미수료자 안내, 감사 대응처럼 다른 업무에서도 사용될 수 있습니다. 따라서 “결과가 맞다”는 사실은 원본 변경을 정당화하지 못합니다.

### 대상자 수는 맞지만 사람이 잘못 포함된 경우

이번에는 AI가 민지와 준호를 발급 대상으로 만들었다고 가정해 보겠습니다. 대상자는 여전히 두 명이므로 단순히 “대상자 수가 2명인가?”만 검사하면 통과할 수 있습니다. 하지만 준호는 과제를 제출하지 않았고, 발급 대상이어야 할 도윤이 빠졌습니다.

이 사례는 집계값만으로 결과를 검증하면 부족하다는 점을 보여 줍니다. 대상자 수뿐 아니라 **누가 포함됐는지**, 그리고 각 사람이 조건을 왜 충족하는지도 확인해야 합니다.

### AI의 완료 보고와 실제 산출물이 다른 경우

AI가 “발급 대상 목록을 생성했습니다”라고 답했지만 실제 파일이 생성되지 않았거나, 파일에는 민지·도윤이 아닌 다른 사람이 들어 있을 수도 있습니다. 자연어 보고는 작업의 증거가 아니라 주장에 가깝습니다.

업무 시스템은 AI의 자기 보고 대신 실제 산출물을 확인해야 합니다. 예를 들어 목록 파일의 존재 여부, 대상자 식별 정보, 수강 기록과의 일치 여부를 검사한 뒤에야 발급 단계로 넘어갈 수 있습니다.

### 조건은 맞지만 허용되지 않은 범위를 수정한 경우

AI가 발급 대상 목록과 함께 알림 메시지 템플릿, 운영자 권한 설정, 지난달 수료증 파일까지 함께 바꿨다고 해 보겠습니다. 변화가 모두 선의에서 비롯되었더라도, 요청받지 않은 변경은 검토와 롤백을 어렵게 만듭니다.

AI에게 맡기는 작업일수록 “무엇을 해야 하는가”뿐 아니라 “무엇을 건드리면 안 되는가”를 함께 정해야 합니다.

## 완료란 무엇인가

이 사례에서 완료는 “AI가 명단을 만들었다”가 아닙니다. 최소한 다음 질문에 답할 수 있어야 합니다.

| 확인할 것 | 질문                                                     |
| --------- | -------------------------------------------------------- |
| 기능 결과 | 민지와 도윤만 발급 대상인가?                             |
| 규칙 적용 | 출석률 80% 이상과 과제 제출 완료 조건을 모두 적용했는가? |
| 원본 보존 | 수강 기록과 과제 제출 기록이 바뀌지 않았는가?            |
| 변경 범위 | 목록 생성에 필요한 파일만 수정했는가?                    |
| 검증 근거 | 누가 다시 확인해도 같은 결론에 도달할 수 있는가?         |

여기서 핵심은 AI를 불신하자는 것이 아닙니다. 사람도 동일한 실수를 할 수 있습니다. 중요한 점은 업무의 품질을 개인의 주의력이나 모델의 응답 품질에만 맡기지 않고, 결과를 확인할 수 있는 구조를 만드는 것입니다.

예를 들어 발급 대상 목록을 만들기 전에 조건을 문서로 고정하고, 생성 후에는 원본 수강 기록과 대상자 목록을 비교하며, 조건이 하나라도 맞지 않으면 실제 발급을 멈추도록 만들 수 있습니다. 이렇게 하면 AI의 답변은 업무 과정의 한 단계가 되고, 완료 판정은 독립적인 기준과 증거에 근거하게 됩니다.

## 기능 구현과 업무 완료 사이

전통적인 개발에서도 테스트 통과와 배포 가능 여부, 배포 성공과 비즈니스 성공은 서로 다른 문제입니다. AI가 개발 과정에 들어오면 이 차이가 더 뚜렷해집니다. AI는 빠르게 코드를 작성하고 여러 파일을 탐색할 수 있지만, 그만큼 작업 범위가 넓어지거나 의도하지 않은 부작용이 생길 가능성도 함께 커집니다.

따라서 AI를 활용한 개발에서 중요한 질문은 다음과 같이 바뀝니다.

```text
AI가 답을 만들었는가?
→ 그 답이 업무 규칙에 맞는가?
→ 그 과정에서 보호해야 할 자산은 안전했는가?
→ 이 판단을 다시 확인할 수 있는가?
```

이 질문들에 답하게 만드는 장치가 바로 하네스 엔지니어링의 출발점입니다.

## 하네스 엔지니어링이란 무엇인가

하네스 엔지니어링은 AI 모델 자체를 바꾸는 일이 아닙니다. **AI가 업무를 수행할 때 어떤 정보를 참고하고, 무엇을 실행할 수 있으며, 어떤 기준을 통과해야 완료로 인정할지를 모델 바깥에서 설계하는 일**입니다.

수료증 발급 예시에서 AI는 대상자 목록을 만들 수 있습니다. 하지만 다음 판단은 AI의 답변만으로 끝낼 수 없습니다.

- 출석률과 과제 제출 조건은 어디에 정의되어 있는가
- 원본 수강 기록을 수정하지 못하도록 어떻게 보호하는가
- 생성한 목록이 실제 수강 기록과 일치하는지 어떻게 검사하는가
- 검사 실패 후 실제 발급을 어떻게 중단하는가
- 나중에 누가 어떤 근거로 발급을 승인했는지 어떻게 확인하는가

하네스는 이런 질문에 대한 답을 업무 흐름 안에 배치합니다. 즉, AI에게 좋은 프롬프트를 한 번 주는 것보다 더 넓은 개념입니다.

## 하네스가 설계하는 책임

하네스는 프로젝트의 규모와 위험도에 따라 다르게 구현할 수 있습니다. 다만 다음 책임은 빠지지 않도록 설계해야 합니다.

| 책임        | 핵심 질문                       | 수료증 발급 예시                                    |
| ----------- | ------------------------------- | --------------------------------------------------- |
| 업무 계약   | 무엇을 성공으로 볼 것인가?      | 출석률 80% 이상, 과제 모두 제출                     |
| 실행 경계   | 무엇을 변경할 수 있는가?        | 발급 대상 목록만 생성하고 원본 기록은 수정하지 않음 |
| 독립 검증   | 결과가 실제로 맞는가?           | 대상자와 수강 기록을 대조                           |
| 실행 제어   | 실패하면 다음에 무엇을 하는가?  | 검증 실패 시 실제 발급을 중단                       |
| 관측과 증거 | 무엇을 했는지 확인할 수 있는가? | 변경 내역, 검사 결과, 승인 기록 보관                |

이 책임은 특정 도구를 도입해야만 생기는 것은 아닙니다. 작은 프로젝트에서는 테스트와 간단한 배포 파이프라인으로 구현할 수 있고, 규모가 커지면 별도의 검증 도구, 권한 정책, 실행 조정 기능으로 분리할 수 있습니다.

## 프롬프트만 잘 쓰는 것과 무엇이 다른가

프롬프트에 “원본 파일을 수정하지 마세요”라고 적는 일은 중요합니다. 하지만 그 문장만으로 원본 파일에 대한 쓰기 권한이 사라지지는 않습니다. AI가 실수하거나, 지시를 잘못 해석하거나, 다른 파일을 함께 수정했을 때 이를 막거나 발견할 장치가 별도로 필요합니다.

마찬가지로 “결과를 검증하세요”라는 요청만으로 검증이 이루어졌다고 볼 수 없습니다. 어떤 데이터를 기준으로 어떤 항목을 비교했는지, 검증 결과가 실제 발급 단계에 반영되는지까지 확인해야 합니다.

하네스 엔지니어링은 AI의 능력을 낮게 평가해서 만드는 장치가 아닙니다. AI가 빠르게 판단하고 작업할 수 있다는 장점을 유지하면서, 그 결과를 업무에 안전하게 연결하기 위한 구조입니다.

## 언제부터 하네스가 필요한가

모든 일회성 작업에 복잡한 시스템이 필요한 것은 아닙니다. 개인 메모를 요약하거나 초안 문구를 만드는 수준이라면, 결과를 사람이 직접 읽고 수정하는 것만으로 충분할 수 있습니다.

반면 다음과 같은 경우에는 하네스 관점이 필요해집니다.

- AI의 결과가 고객, 수강생, 운영 데이터처럼 실제 업무 대상에 영향을 주는 경우
- 여러 파일·시스템을 읽거나 수정해야 하는 경우
- 규칙 위반이나 원본 훼손의 비용이 큰 경우
- 같은 작업을 반복해서 수행해야 하는 경우
- 작업 결과를 다른 사람이나 시스템이 신뢰하고 이어받아야 하는 경우

중요한 것은 처음부터 거대한 플랫폼을 만드는 일이 아닙니다. 보호해야 할 자산과 실패 비용에 맞춰, 필요한 계약·검증·권한·기록을 조금씩 추가하는 것입니다.

## 정리

- 기능 결과가 맞더라도 원본 데이터 훼손, 규칙 누락, 변경 범위 초과가 있으면 업무는 실패할 수 있습니다.
- AI의 완료 보고는 주장일 뿐이므로 실제 산출물과 업무 규칙을 독립적으로 확인해야 합니다.
- 하네스 엔지니어링은 AI 주변에 계약, 실행 경계, 검증, 실패 제어, 기록을 설계하는 일입니다.
- 하네스의 목적은 AI를 제한하는 것이 아니라 AI의 결과를 업무에 안전하게 연결하는 것입니다.
- 하네스의 구현 수준은 프로젝트 규모보다 보호할 자산과 실패 비용에 맞춰 결정해야 합니다.
