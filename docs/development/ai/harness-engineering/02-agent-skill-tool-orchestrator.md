## Agent, Skill, Tool, Orchestrator는 무엇이 다른가

1편에서는 AI가 정확한 결과를 만들었더라도 업무 전체는 실패할 수 있음을 살펴봤습니다. 그렇다면 업무 규칙, 구현, 검증, 승인 흐름을 누가 어떤 방식으로 맡아야 할까요?

하네스 엔지니어링에서는 이 질문을 설명하기 위해 Agent, Skill, Tool, Orchestrator라는 네 역할을 자주 구분합니다. 이들은 반드시 네 개의 제품이나 네 명의 AI를 뜻하지 않습니다. 업무에서 서로 다른 종류의 책임이 뒤섞이지 않도록 돕는 설계 언어에 가깝습니다.

## 먼저 짚을 오해

하네스를 도입하려면 Agent, Skill, Tool, Orchestrator를 각각 별도 서비스로 구축해야 한다고 생각하기 쉽습니다. 하지만 작은 프로젝트에서 이는 불필요하게 복잡할 수 있습니다.

예를 들어 수료증 발급 대상 목록을 만드는 작은 내부 도구라면, AI가 코드를 수정하고 기존 테스트를 실행한 뒤 CI가 통과 여부에 따라 배포를 막는 구조만으로도 충분할 수 있습니다. 이 경우 AI는 Agent 역할을, 테스트 함수는 Tool 역할을, 검증 절차 문서는 Skill 역할을, CI 파이프라인은 Orchestrator 역할을 합니다.

중요한 것은 네 요소의 이름이나 개수가 아닙니다. **판단이 필요한 일, 반복 절차, 결정적 실행, 다음 단계의 제어가 각각 어떤 책임인지 구분하고 있는가**가 중요합니다.

## 네 가지 책임

| 요소         | 핵심 질문                        | 수료증 발급 예시                       |
| ------------ | -------------------------------- | -------------------------------------- |
| Agent        | 다음에 무엇을 판단하고 수행할까  | 대상자 목록 생성 로직의 변경 방법 조사 |
| Skill        | 반복 업무를 어떤 절차로 수행할까 | 변경 후 검사 순서와 보고 형식          |
| Tool         | 정해진 입력에 어떤 결과를 낼까   | 특정 수강생의 출석·과제 상태 조회      |
| Orchestrator | 언제 진행·중단·재시도할까        | 검증 통과 뒤에만 발급 승인             |

수료증 발급 예시를 전체 흐름으로 놓으면 다음과 같습니다.

```text
발급 조건 확인
→ 대상자 목록 생성 또는 생성 로직 수정
→ 대상자·원본 기록 검증
→ 검증 통과 시에만 발급 승인
```

한 사람이 이 모든 일을 할 수도 있고, 하나의 프로그램 안에서 처리할 수도 있습니다. 다만 각 단계가 어떤 성격의 일인지 구분해야 검증 누락이나 권한 혼선을 줄일 수 있습니다.

## Agent: 판단이 필요한 실행 주체

Agent는 주어진 목표와 제약 안에서 다음 행동을 판단하는 실행 주체입니다. 코드베이스를 살펴보고, 어떤 파일을 수정해야 하는지 결정하고, 오류 원인을 추적하고, 사용할 도구를 선택하는 일이 Agent에 가깝습니다.

수료증 발급 시스템에 새 조건이 추가되었다고 가정해 보겠습니다.

> 출석률과 과제 제출 조건은 유지하되, 수강료 미납자는 발급 대상에서 제외해 주세요.

이 요청을 처리하려면 기존 조건이 어디에 구현돼 있는지, 미납 정보는 어느 데이터에서 읽어야 하는지, 기존 테스트에는 어떤 사례가 부족한지 조사해야 합니다. 정해진 하나의 함수 호출만으로는 해결하기 어렵고, 상황을 읽고 다음 행동을 선택해야 합니다. 이런 종류의 일에 Agent가 적합합니다.

반대로 “민지의 출석률은 몇 퍼센트인가?”처럼 입력과 출력이 확정된 조회를 Agent의 추론에 맡길 필요는 없습니다. 그 경우에는 결정적인 Tool이 더 적합합니다.

## Skill: 반복 가능한 절차

Skill은 Agent가 따라야 할 재사용 가능한 업무 절차입니다. Agent가 무엇을 할지 판단한다면, Skill은 같은 종류의 일을 할 때 어떤 순서와 기준을 반복할지 알려 줍니다.

예를 들어 발급 대상 로직을 변경한 뒤에는 매번 다음을 확인해야 할 수 있습니다.

1. 변경된 규칙과 변경 금지 대상을 확인합니다.
2. 대상자 목록을 생성합니다.
3. 대상자별 출석률·과제 제출·미납 상태를 비교합니다.
4. 원본 수강 기록이 바뀌지 않았는지 확인합니다.
5. 실패 항목과 검사 결과를 남깁니다.

이 절차를 매번 긴 프롬프트로 다시 작성하는 대신, 문서나 실행 지침으로 묶어 재사용할 수 있습니다. 그것이 Skill입니다.

다만 Skill이 존재하거나 호출되었다고 해서 검증이 끝난 것은 아닙니다. “검증 절차를 따르라”는 지침과 실제로 비교 프로그램을 실행해 통과했다는 증거는 별개입니다.

## Tool: 결정적인 실행 수단

Tool은 정해진 입력을 받아 명확한 동작을 수행하고 구조화된 결과를 반환하는 수단입니다. Tool의 핵심은 자율적인 판단이 아니라 예측 가능한 입력·출력 계약입니다.

예를 들어 아래와 같은 도구를 생각할 수 있습니다.

```text
get_learner_status("민지")
→ { 출석률: 92, 과제_제출: true, 수강료_납부: true }
```

또는 대상자 목록을 검증하는 도구는 다음과 같은 결과를 반환할 수 있습니다.

```text
verify_certificate_candidates(...)
→ { ok: true, invalid_candidates: [], source_unchanged: true }
```

이처럼 Tool은 대상자 상태 조회, 규칙 계산, 파일 무결성 비교, 테스트 실행처럼 반복해도 같은 입력에는 같은 결과가 나와야 하는 작업에 적합합니다. AI가 수강 기록을 읽고 “아마 민지는 대상일 것 같습니다”라고 답하는 방식보다 감사와 재현에 유리합니다.

Tool은 가능한 한 권한을 좁게 설계하는 편이 좋습니다. 조회만 필요한 도구에 수강 기록 수정이나 수료증 발급 권한까지 함께 넣으면, 단순 조회 요청도 불필요한 위험을 갖게 됩니다.

## Orchestrator: 순서와 실패 전파

Orchestrator는 여러 단계의 결과를 바탕으로 다음에 진행할지, 중단할지, 재시도할지를 정합니다. 별도의 감독 AI일 수도 있지만, 고정된 흐름이라면 일반 애플리케이션 코드나 CI 파이프라인으로 충분합니다.

수료증 발급의 흐름을 예로 들면 다음과 같습니다.

```text
대상자 생성
→ 대상자 규칙 검증
→ 원본 무결성 검증
→ 둘 다 통과한 경우에만 발급 승인
```

여기서 대상자 규칙 검증이 실패했다면, 실제 수료증 발급 단계는 실행하면 안 됩니다. 원본 무결성 검사에 실패했다면, 목록이 맞더라도 승인해서는 안 됩니다. Orchestrator는 이처럼 검증 결과를 다음 단계의 조건으로 바꿉니다.

재시도 정책도 이 역할과 연결됩니다. 외부 출석 시스템의 일시적인 응답 실패는 제한적으로 재시도할 수 있습니다. 반면 과제 미제출자가 목록에 포함된 규칙 위반은 같은 요청을 반복한다고 해결되지 않으므로 즉시 중단하고 원인을 수정해야 합니다.

## 무엇을 어디에 둘지 결정하는 기준

네 요소를 구분할 때는 “AI가 할 수 있는가?”보다 “이 일에 판단이 필요한가, 결과가 결정적인가, 반복 절차인가, 다음 단계의 조건인가?”를 먼저 물어보는 편이 좋습니다.

### 단순 조회와 계산

입력과 출력이 명확한 조회·계산은 Tool에 둡니다. 예를 들어 특정 수강생의 출석률 조회, 수료 조건 충족 여부 계산, 원본 파일 변경 여부 비교가 이에 해당합니다.

이런 일을 Agent에게 맡기면 결과가 자연어 설명에 의존하고, 같은 조건을 일관되게 처리하기 어렵습니다.

### 코드 변경과 조사

여러 파일을 읽고 요구사항을 해석하며 구현 방법을 선택해야 한다면 Agent가 적합합니다. 새 발급 조건을 기존 시스템에 반영하거나, 검증 실패 원인을 조사하는 일이 대표적입니다.

다만 Agent가 코드를 수정했다는 사실은 기능이 맞다는 증거가 아닙니다. 수정 뒤에는 Tool과 검증 절차가 뒤따라야 합니다.

### 반복 검증

여러 변경에서 같은 확인 순서가 반복된다면 Skill로 묶습니다. 특히 “원본 보존 확인 → 대상자 규칙 검사 → 결과 기록”처럼 누락하면 위험한 절차는 재사용 가능한 형태로 만드는 편이 좋습니다.

Skill을 너무 넓게 만들 필요는 없습니다. 모든 개발 작업에 적용되는 거대한 Skill보다, 언제 사용하고 언제 사용하지 않는지가 분명한 작은 절차가 더 유용합니다.

### 승인과 중단

선행 단계의 성공 여부에 따라 다음 작업을 제어해야 한다면 Orchestrator의 책임입니다. 대상자 목록 생성이 성공했다는 AI의 보고만으로 발급을 진행하지 않고, 필요한 검증이 모두 통과했을 때만 승인해야 합니다.

반대로 정해진 순서의 함수 몇 개를 호출하는 간단한 작업이라면 복잡한 감독 Agent를 추가할 필요가 없습니다. 단순한 코드나 CI 게이트로도 충분히 명확하게 제어할 수 있습니다.

## 정리

- Agent는 목표와 제약을 해석해 다음 행동을 판단하는 실행 주체입니다.
- Skill은 반복 업무에서 지켜야 할 절차와 보고 기준을 재사용하는 방법입니다.
- Tool은 명확한 입력·출력 계약을 가진 결정적인 실행 수단입니다.
- Orchestrator는 단계의 순서와 조건을 관리하고, 실패가 다음 단계로 전파되도록 만듭니다.
- 네 요소는 반드시 각각 독립된 제품이나 AI여야 하는 것이 아니라, 책임이 섞이지 않게 하는 설계 기준입니다.
