# TLS·인증서와 방화벽의 기본 개념

## 왜 암호화와 인증이 필요한가

암호화되지 않은 데이터를 네트워크로 전송하면 통신 경로에서 패킷을 가로챌 수 있는 공격자에게 내용이 노출될 수 있다.

예를 들어 평문 HTTP로 로그인 정보를 전송하면 계정 정보나 비밀번호가 그대로 노출될 수 있다.

```text
평문 HTTP

POST /login HTTP/1.1
Host: example.com

username=alice&password=secret123

→ 패킷을 보면 내용을 그대로 확인할 수 있음
```

HTTPS에서는 HTTP 메시지를 TLS로 보호하기 때문에 중간에서 패킷을 보더라도 HTTP 요청의 내용을 그대로 읽을 수 없다.

TLS가 제공하는 핵심 기능은 다음 세 가지다.

| 기능                    | 의미                                        |
| ----------------------- | ------------------------------------------- |
| 기밀성(Confidentiality) | 제3자가 통신 내용을 읽지 못하게 한다        |
| 무결성(Integrity)       | 통신 중 데이터가 변조되지 않았는지 확인한다 |
| 인증(Authentication)    | 통신 상대가 의도한 상대인지 확인한다        |

## TLS: 웹 통신의 기본 보안 계층

`TLS(Transport Layer Security)`는 네트워크 통신을 보호하기 위한 보안 프로토콜이다.

과거에 사용되던 `SSL(Secure Sockets Layer)`의 후속 프로토콜이며, 오늘날에는 SSL이 아닌 TLS를 사용한다. 다만 관습적으로 `SSL 인증서`, `SSL/TLS` 같은 표현이 여전히 사용된다.

HTTPS는 간단히 다음과 같이 이해할 수 있다.

```text
HTTPS = HTTP over TLS
```

TLS 연결을 시작할 때는 먼저 **TLS Handshake**가 이루어진다.

핸드셰이크 과정에서는 대략 다음 작업을 수행한다.

1. 사용할 TLS 버전과 암호 알고리즘을 협상한다.
2. 서버가 인증서를 전달하고 클라이언트가 이를 검증한다.
3. 키 교환을 통해 양쪽이 공유 비밀을 만든다.
4. 공유 비밀로부터 실제 통신에 사용할 키를 생성한다.
5. 이후 애플리케이션 데이터를 암호화하여 통신한다.

TLS에서는 인증과 키 교환 등에 비대칭키 기반 기술을 사용하고, 실제 데이터 통신에는 빠른 대칭키 암호 기술을 사용한다.

```text
TLS Handshake
→ 서버 인증 + 키 교환
→ 세션에서 사용할 키 생성

이후 통신
→ 대칭키 기반으로 데이터 보호
```

## 인증서(Certificate)의 역할

HTTPS 사이트에 접속하면 서버는 자신의 인증서를 클라이언트에게 전달하고, 브라우저는 이를 검증한다.

| 확인 사항   | 내용                                         |
| ----------- | -------------------------------------------- |
| 인증서 체인 | 신뢰하는 CA까지 유효하게 연결되는가          |
| 전자서명    | 인증서의 서명이 올바른가                     |
| 도메인      | 인증서의 도메인과 접속한 도메인이 일치하는가 |
| 유효 기간   | 인증서가 현재 유효한가                       |

문제가 있으면 브라우저가 인증서 경고를 표시할 수 있다.

`CA(Certificate Authority)`는 인증서를 발급하고 전자서명하는 기관이다.

인증서는 **서버의 공개키와 도메인 등의 신원 정보를 연결**하고, CA의 전자서명을 통해 그 연결을 검증할 수 있게 한다.

```text
CA
 │
 │ 전자서명
 ▼
인증서
├─ 도메인 정보
├─ 공개키
└─ 유효 기간 등
```

여기서 CA가 해당 사이트 자체가 안전하다고 보증하는 것은 아니다.

```text
인증서가 정상이다
≠ 사이트가 해킹되지 않았다
≠ 사이트에 악성 코드가 없다
≠ 사이트 운영자를 무조건 신뢰할 수 있다
```

인증서는 기본적으로 **해당 공개키가 특정 도메인 등의 신원과 연결되어 있음을 검증하는 수단**이다.

## IPsec: 네트워크 계층의 보안

`IPsec(IP Security)`은 IP 계층에서 통신을 보호하기 위한 프로토콜 모음으로 VPN에서 많이 사용된다.

TLS가 주로 특정 애플리케이션의 통신을 보호한다면, IPsec은 IP 패킷 수준에서 통신을 보호할 수 있다.

| 구성 요소                           | 역할                                                    |
| ----------------------------------- | ------------------------------------------------------- |
| AH(Authentication Header)           | 무결성과 출처 인증 등을 제공하며 암호화는 하지 않음     |
| ESP(Encapsulating Security Payload) | 암호화를 통한 기밀성을 제공하며 무결성·인증도 제공 가능 |
| IKE(Internet Key Exchange)          | 상대 인증, 보안 설정 협상 및 키 교환                    |

현대적인 IPsec 환경에서는 주로 ESP가 사용되며 AH는 상대적으로 드물게 사용된다.

## 방화벽: 네트워크의 경비원

방화벽은 네트워크 경계나 개별 호스트에서 **정해진 정책에 따라 네트워크 트래픽을 허용하거나 차단**한다.

| 유형            | 위치               | 특징                        | 예시                             |
| --------------- | ------------------ | --------------------------- | -------------------------------- |
| 네트워크 방화벽 | 네트워크 경계      | 여러 시스템의 트래픽을 제어 | Cisco, Palo Alto 등의 방화벽     |
| 호스트 방화벽   | 개별 컴퓨터        | 해당 호스트의 트래픽을 제어 | ufw, Microsoft Defender Firewall |
| WAF             | 웹 애플리케이션 앞 | HTTP 요청 내용을 분석       | AWS WAF, Cloudflare WAF          |

일반적인 네트워크 방화벽은 IP, 포트, 프로토콜 등을 기준으로 트래픽을 제어한다.

```text
외부 → TCP 443  → 허용
외부 → TCP 3306 → 차단
```

반면 `WAF(Web Application Firewall)`는 URL, HTTP Header, Request Body 등 HTTP 요청의 내용을 분석해 웹 공격을 탐지하거나 차단한다.

방화벽 정책은 크게 다음과 같이 생각할 수 있다.

- **Default Deny**: 명시적으로 허용한 통신만 통과시키고 나머지는 차단
- **Default Allow**: 명시적으로 차단한 통신만 막고 나머지는 허용

보안이 중요한 환경에서는 필요한 통신만 허용하는 **최소 권한 원칙(Least Privilege)**에 따라 Default Deny 방식이 일반적으로 적합하다.

## 포트 스캔: 열린 포트 확인하기

포트 스캔은 시스템에서 외부에 노출된 포트의 상태를 확인하는 방법이다.

`nmap` 같은 도구를 이용하면 관리자가 자신이 관리하거나 점검 권한이 있는 시스템에서 어떤 포트와 서비스가 외부에 노출되어 있는지 확인할 수 있다.

대표적인 TCP 포트 상태는 다음과 같다.

| 상태     | 의미                                                                     |
| -------- | ------------------------------------------------------------------------ |
| open     | 해당 포트에서 서비스가 연결을 받을 수 있는 상태                          |
| closed   | 호스트에는 도달했지만 해당 포트에서 대기 중인 서비스가 없는 상태         |
| filtered | 방화벽이나 네트워크 필터 때문에 open인지 closed인지 판단하기 어려운 상태 |

방화벽에서 특정 포트를 허용했다고 해서 해당 포트가 자동으로 `open`이 되는 것은 아니다.

예를 들어 방화벽에서 443번 포트를 허용했더라도 웹 서버가 해당 포트에서 실행되고 있지 않다면 `open`으로 보이지 않는다.

반대로 웹 서버가 443번 포트에서 실행 중이어도 방화벽이 해당 통신을 차단하면 외부에서 접근할 수 없다.

```text
외부에서 서비스에 접근하려면

서비스가 해당 포트에서 Listen
        +
방화벽에서 통신 허용
        +
네트워크 경로상 접근 가능
```

또한 서비스가 `127.0.0.1` 같은 로컬 인터페이스에만 bind되어 있다면 외부에서는 접근할 수 없다.

즉 **방화벽의 포트 허용 여부와 실제 서비스의 실행·Listen 상태는 서로 다른 개념**이다.

## 정리

- 암호화되지 않은 네트워크 통신은 통신 경로를 관찰할 수 있는 공격자에게 내용이 노출될 수 있다.
- TLS는 통신의 기밀성, 무결성, 인증을 제공하며 HTTPS는 HTTP 통신을 TLS로 보호하는 방식이다.
- TLS 핸드셰이크에서는 서버 인증과 키 교환 등을 수행하고, 이후 생성된 키를 이용해 데이터를 안전하게 주고받는다.
- 인증서는 공개키와 도메인 등의 신원 정보를 연결하고, CA의 전자서명을 통해 이를 검증할 수 있게 한다.
- IPsec은 IP 계층에서 통신을 보호하며 VPN에서 많이 사용된다.
- 방화벽은 IP·포트 등의 정책에 따라 트래픽을 허용하거나 차단하고, WAF는 HTTP 요청 내용을 분석해 웹 애플리케이션을 보호한다.
- 방화벽에서 포트를 허용하는 것과 실제 서비스가 해당 포트에서 Listen하는 것은 서로 다른 개념이다.
- 포트 스캔의 `open`, `closed`, `filtered`는 외부에서 관찰되는 서비스 상태와 네트워크 필터링 상태를 나타낸다.
